# r3 设计理念（大白话版）

> 给谁看：刚入门逆向一年的你——会基础编程、懂点计算机知识，但不搞开发。
> 这份文档讲清楚 r3 为什么这么设计、每个设计在解决什么问题、实测发现的真相和坑，
> 以及 v1.1 补上的设计缺口。配套文档：`PLAN.md`（v1）、`PLAN-v1.1.md`、`PLAN-v1.2.md`、`PLAN-v1.3.md`、`PLAN-v2.md`、`PLAN-v2.1.md`。

## 1. r3 是干什么的：一句话 + 一个比喻

**r3 = 给 AI agent 用的 radare2 常驻外包装（传声筒 + 常驻保姆）。**

r2（radare2）是个"重家伙"：打开一个二进制、做全量分析（`aaa`）可能要几分钟，
分析完的状态（函数表、反汇编、字符串索引、你设的配置）全都住在 r2 进程的内存里。
但 AI agent 每次干活都开一个**新的 bash 进程**，进程一结束，r2 跟着死，状态全丢。
等于每次都要把重家伙重新搬上楼、重新分析一遍——大文件一次几分钟，agent 根本等不起。

r3 的做法：雇一个"保姆"（daemon）常驻后台，把 r2 抱在怀里不撒手，分析状态一直活着。
agent 每次想用 r2，就喊一声"保姆，帮我问 r2 一个问题"；保姆转述命令、把答案原样带回来。
agent 不直接碰 r2，也永远不用重新分析。

```
agent（短命 bash）
   │  每次调用 r3 "<r2命令>"
   ▼
r3 CLI（传声筒，薄客户端）──Unix socket──► r3 daemon（保姆，常驻后台）
                                              │ 抱着不撒手
                                              ▼
                                          r2 进程（分析状态常驻内存）
                                              │
                                     ~/.cache/r3/（工程缓存 + 日志 + 最近记录）
```

## 2. 它解决了什么痛点

| 裸 r2 的典型用法 | 痛点 |
|---|---|
| `r2 -q -c "afl" file` | 每次从零开始：重新 open + 重新分析 |
| `r2 -q -c "aaa" -c "pdf @ main" file` | 大文件 `aaa` 几分钟，每次都是白等 |
| 状态不能跨命令保留 | 设过的配置（`e asm.bytes=false`）、看过的函数表，下次全没了 |

r3 的解法：**状态常驻 + 缓存秒开**。实测同文件第二次 `open` 约 0.12 秒出结果。

## 3. 设计理念逐个讲

### 3.1 常驻 daemon —— "状态跨 bash 调用存活"是灵魂

这是 r3 和裸 r2 的本质区别。daemon 是一个常驻后台进程（懒启动：连不上就自动拉起），
它抱着唯一的 r2 进程。分析状态、r2 配置、最近命令、当前文件，全住在 daemon 里，
所以跨 bash 调用存活。v1 是单会话（daemon 只抱一个 r2、只开一个文件），
但通信协议里预留了 `sid`（会话 id）字段，将来多会话只动 daemon。

### 3.2 CLI 是"传声筒"，不是翻译官

v1 的一个硬决策（PLAN 决策 #4）：**r3 不做命令翻译层**。agent 本来就会 r2 方言，
r3 只负责把命令原样转给 r2、把输出原样带回。好处：透明、零学习成本、r2 全部命令可用；
代价：r2 的"报错"只是输出文本，r3 不帮解释；agent 发错命令，r3 也只会把错误文本带回来。

透传还有一个"副产品特性"：agent 用 `r3 "e asm.bytes=false"` 设的配置会常驻生效——
因为 daemon 有状态，配置命令本身就是一条普通的 r2 命令。

v2 起调试命令同样只是透传：`r3 open <文件> --debug` 只负责把会话的“调试态”管对
（启动方式、自愈保持、输出干净、状态可见），agent 会什么 r2 调试命令（`db`/`dc`/
`dr`/`wx`/`dbt`）就发什么，r3 不新增翻译层。

v2.1 的报错富化同样不违背透传：r3 不改 r2 的任何输出，只在 r3 **自己的错误消息**里
附上 r2 stderr 尾行（真实病因），r2 命令输出本体仍原样带回。

### 3.3 管道协议 —— 对讲机协议

daemon 用 `r2 -q0 -` 把 r2 跑成管道模式（`-` = 命令来自 stdin，不带文件常驻）。
协议极简：**向 r2 的 stdin 写"命令+换行"，从 stdout 读到 NUL（`\x00`）就算这条命令的输出结束**。
像对讲机：按一下说一句，说完松手（NUL 就是"我说完了"的记号）。

实测才发现的协议真相（已写进代码注释存档）：
1. r2 启动后会先发一个**空 NUL**，表示"我准备好了"。
2. 每条命令前后，r2 会在 **stderr**（不是 stdout！）打 1~3 份鼠标禁用序列
   （`\x1b[?1000...l`），而且没有任何配置能关掉。所以 daemon 把 stderr 单独导到
   `daemon.log`，stdout 的命令输出天然干净无 ANSI——不需要改写输出，传声筒保持透明。
3. `scr.pager=cat` 是长输出不挂死的关键：空字符串 `scr.pager=` 在管道模式下不生效，
   会导致 `izz` 等长输出命令挂起等 stdin（8 秒超时才被看门狗杀掉）。

### 3.4 缓存 —— "同一本书，第二次翻不用重读"

- **钥匙** = 文件内容的 SHA-256 + r2 版本号。r2 升级后旧工程可能不兼容，版本号入键自动作废。
- 第一次 `open`：`o` 打开 → `aaa` 分析 → `Ps` 把整个工程（含分析结果）存到
  `~/.cache/r3/projects/<钥匙>`。
- 第二次 `open`（同文件）：直接 `Po` 读工程，秒开。
- 比喻：第一次看书把重点抄进笔记本，第二次直接翻笔记本，不用重读原书。
- 工程是 git 仓库形态的文件；`Ps` 存到精确路径文件（不自动加 `.r2` 后缀），
  `Po` 恢复（会打一条 deprecation warning 走 stderr，无副作用）。
- **归属校验（v1.1）**：每个工程缓存旁写 `<钥匙>.meta.json`，记录"这份缓存属于哪个
  文件的 SHA-256"。meta 缺失或对不上（含 v1 旧缓存）一律视为未命中：删脏缓存、
  重新分析，污染缓存永远不会被误用。

### 3.5 懒启动 + 看门狗 + 黑名单 —— 保姆的自我保护

- **懒启动**：CLI 连不上 socket 就自动在后台拉一个 daemon（脱离终端、日志重定向），
  然后轮询等它就绪（上限约 5 秒）。agent 完全不用手动管 daemon。
- **看门狗**：单条命令默认 900 秒超时（大文件 `aaa` 很慢，不能设短）。超时 → 杀掉 r2 →
  重新拉起 → 按 `state.json` + 缓存自动恢复现场 → 明确告诉 agent"超时了，已自愈"。
  环境变量 `R3_CMD_TIMEOUT`（秒）可覆盖。v2 实测：r2 死时 debuggee 不会自动清理
  （无 PTRACE_O_EXITKILL），r3 用 `start_new_session` + `os.killpg` 主动全组清理；
  调试会话自愈后按原 `debug` 模式重建，现场 `aaa` 固定用默认超时。
- **交互命令黑名单**：`V`、`Vv`、`Vi`、`ve` 等 visual 系列会霸占终端、把管道挂死，
  r3 直接拒绝（CLI 退出码 2），防止 daemon 的 r2 管道被搞死。
- **并发安全**：daemon 单线程串行处理命令。两个 agent 同时敲 r3 只是排队，不会打架。

### 3.6 输出处理 —— "干净 + 透明 + 防刷屏"

- daemon 启动参数固定 `-e scr.color=0 -e scr.interactive=0 -e scr.pager=cat`（无色、无交互、无分页器）。
- 默认截断到 20000 字符（`R3_MAX_OUT` 可调），截断时结尾加横幅提示自救方法
  （`~` 过滤器、`--full`、`R3_MAX_OUT`）。
- **JSON 永不截断（v1.1）**：输出以 `{` 或 `[` 开头（`aflj`/`izzj`/`ij` 等）判定为
  JSON，跳过截断——agent 拿到的 JSON 一定完整可 `json.loads`。
- 不解析、不改写命令输出——传声筒保持透明。
- 退出码语义（v1）：0 = 成功；1 = daemon/连接故障；2 = 交互命令被黑名单拒绝；
  3 = 命令超时（daemon 已自愈）。r2 层面的"报错"体现在输出文本里，不影响退出码。

## 4. 实测发现的"真相"和坑（v1 代际积累）

1. **r2 的 `o` 不会关旧文件，也不会清分析** —— 这是 v1 最严重 bug 的根源（见第 5 节）。
2. stderr 是 r2 的"垃圾场"（鼠标禁用序列、deprecation warning、git hint），stdout 是干净通道。
3. r2 的 `o`（打开文件）会重置 pager 配置，daemon 每次 open 后必须重发 `e scr.pager=cat`。
4. `!sleep N` 在管道模式下精确阻塞 N 秒（看门狗验收靠它测试）。
5. 同内容、不同路径打开时缓存按内容命中，`Po` 后 r2 内部指向旧路径——影响很小，v1 接受。

## 5. 实测复现的 v1 重大 bug：跨文件分析状态污染

这是评测里"关键正确性 bug"的根因，我用 r2 管道模式（= daemon 内部的实际行为）完整复现了：

```
o /bin/ls  →  aaa  →  afl~main   →  ls 的 main（0x4da0，381 字节）        ✓ 正常
o /bin/true                        （注意：并没有关掉 ls！）
i~file      →  /bin/true           （bin 层：当前文件已切到 true）        ✓ 对
afl~main    →  还是 ls 的 main                                        ✗ 错
aaa（再分析）→  还是 ls 的 main                                       ✗ 错
o 列表      →  ls(fd4) 和 true(fd7*) 同时在开                           ← 铁证
```

**根因（三条硬事实）**：
1. r2 的 `o 新文件` = "**再开**一个文件并切到它"——旧文件还开着（fd 不关），
   旧分析原封不动（`aaa` 也不会清）。
2. `i~file` / `iS` / `izz` 读的是"当前 bin"（所以显示新文件），而 `afl` / `pdf` / `pd`
   读的是"分析核心"（还是旧文件的数据）→ **同一时刻两个视角对不上**，
   这就是评测里"函数列表/反汇编静默答错文件"的机制。
3. `Ps` 会把当前分析核心（含旧文件数据）原样存进"**新文件钥匙**"的缓存目录
   → 污染被固化进缓存，restart + `Po` 后依然错。pd 也连带坏：分析元数据是旧文件的，
   新文件代码区被打成 `.string`。

**修复（v1.1 已实现）**：
- 换文件时**杀掉 r2 进程重开一个新的**（`reset_r2`：从零开始，100% 干净；代价是
  切换文件后 agent 设过的 `e` 配置会重置，需要重设——同文件会话内不受影响，
  open 切换时输出会明确提示）。
- 缓存加**归属校验**（meta 文件记录"这份缓存属于哪个文件"，校验不过就删脏缓存
  重新分析）。
- `pd` 连带坏随之自动修复（分析核心干净了，反汇编自然正确）。
- 详细设计见 `PLAN-v1.1.md`；`tests/acceptance.sh`（A–J 组）全绿。

## 6. v1.1 补上的缺口（已实现）

| 缺口 | 问题 | v1.1 实现 |
|---|---|---|
| 跨文件污染 | `o` 不关旧文件不清分析，缓存被污染固化 | 换文件杀 r2 重开（决策 #9）+ 缓存归属校验 meta（决策 #10） |
| 沙箱不友好 | 缓存/日志/socket 全在工作区外，workspace-write 沙箱下 daemon 起不来 | 路径可配置（`R3_CACHE_DIR` / `R3_SOCK_PATH`）+ `R3_NO_CACHE=1` 纯内存模式 + 目录不可写自动降级（决策 #12） |
| JSON 被切断 | 20000 字符截断把 `aflj`/`izzj` 切成非法 JSON | JSON 输出永不截断（按输出首字符 `{`/`[` 判断，决策 #11） |
| pd 连带坏 | 分析元数据错 → 新文件反汇编被打成 `.string` | 随第 1 项修复，无需单独设计 |
| 顺手配套 | 无清理命令、status 缓存计数把目录也计入 | `r3 cache-clean`（决策 #13，可选但已实现）+ 计数修正 |

## 7. v2 / v2.1 动态调试（#31–#44 理念与边界）

- **入口**：`r3 open <文件> --debug`，daemon 用 `r2 -d` 拉起目标并停在 r2 初始断点；
  同一文件 static/debug 互斥，切换时杀旧 r2 以目标模式重开。
- **静音**：daemon 写临时 `dbg.profile`（无输入文件时内容 `stdio=/dev/null`，无空格）
  让目标程序 stdio 不混进 r3 的 NUL 分帧；agent 看不到目标 printf，如需输出让目标
  自己写文件。
- **stdin 注入**：`r3 open <文件> --debug --stdin <输入文件>` 走 dbg.profile 的
  `stdin=<绝对路径>` + stdout/stderr=/dev/null 三行组合。输入是**拉起时快照**：
  运行中向文件追加无效；换输入必须重新 open（会重新拉起目标，PID 会变）。
- **不落盘**：debug 会话恢复禁 `o`/`Po`（Po 会破坏调试态），现场 `aaa` 只在会话内存，
  不 `Ps`/不写 meta；工程缓存只由 static 会话读写。
- **清理**：r2 不会自动带走 debuggee；r3 每次 close/超时/daemon 退出用 killpg 全组
  清理（目标自行 setsid 改进程组的边界已写文档）。
- **报错富化与预检**：debug 拉起失败时 r3 自己的错误消息带 r2 stderr 尾行；预检只查
  目标 isfile/R_OK/X_OK，缺执行位直接提示 `chmod +x`，**不替 agent 改权限**。
- **失败回滚**：模式切换失败回滚为旧模式并标 `[启动失败待重开]`；后续普通命令自动
  按旧模式重建（自动自愈），status/sessions 如实显示。
- **边界**：只做拉起式调试；attach 受内核 yama ptrace_scope=1 限制不可用（错误文本
  原样透出）；ESIL/远程/内核调试明确排除。

## 7.5 v2.1 修复与输入注入（#39–#44 大白话）

v2.0 的调试链路能跑通，但实战中暴露了三件“账本对不上/病因看不见/嘴喂不进”的问题：

- **报错富化 + 预检（#39/#40）**：以前 debug 拉起失败只甩一句“没收到就绪 NUL”，
  真正原因（比如目标没有执行权限，r2 还报成误导的 “Cannot open ... for writing”）
  埋在 daemon.log 里。现在 r3 把 r2 stderr 最近一段抓进 ring buffer，失败时清洗
  ANSI 后把尾行附在 r3 自己的错误消息里；同时在拉起前先查文件在不在、能不能读、
  能不能执行，缺执行位直接说 `chmod +x`。预检只提示，不替 agent 改权限。
- **失败回滚 + 待重开 + 自动自愈（#41）**：以前 static→debug 切换失败会杀掉旧
  会话却把账本改成 debug，status 还显示调试成功——agent 会拿着假会话继续干活。
  现在失败就把账本滚回旧模式、r2 置空、标 `[启动失败待重开]`；下一次任何普通
  命令都会先按旧模式自动重建，重建成功就清标记，agent 不用手动处理。
- **stdin 注入 + 换输入重拉（#42/#43）**：交互式目标（密码、游戏输入）调试时喂
  不进 stdin。现在 `r3 open ./crackme --debug --stdin ./input.txt` 通过
  dbg.profile 的 rarun2 `stdin=` 在拉起时快照式喂入；运行中追加无效，换输入 =
  重新 open（旧 r2 和 debuggee 一并清掉后重新拉起，并现场重做分析）。
- **状态可见 + 交付（#44）**：status/sessions 文本显示 `[输入文件: 路径]` 和
  `[启动失败待重开]`，JSON 加 `stdin_file`/`startup_failed`；版本号 v2.1.0，
  AGENTS/DESIGN/SKILL/acceptance 全部同步。

## 8. 一句话总结

r3 的设计哲学：**用常驻 daemon 换"状态跨调用存活"，用工程缓存换"秒开"，
用透明传声筒换"零学习成本"，用黑名单/看门狗换"不挂死"**。
v1.1 的目标是把"状态可信"从口号变成事实——**每一条分析结果都保证属于当前打开的文件**。
